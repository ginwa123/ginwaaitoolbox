- [zig@0.15] **CRITICAL: Never return stack-allocated slices from functions** — stack memory is invalidated after function returns, causing corruption. Always use `allocator.alloc()` or `allocator.dupe()` for returned slices.
- [zig@0.15] `{s}` format string requires `[]u8` — use `@errorName(err)` to convert error types to string
- [zig@0.15] ArrayList API changed: `.init` → `.empty`, all of `.appendSlice`, `.deinit`, `.toOwnedSlice` now require allocator as first arg
- [zig@0.15] `std.fs.File.createFile` replaces `writeFile` for creating/overwriting files
- [zig@0.15] `ArrayList.deinit` requires allocator parameter
- [zig@0.15] Line collection must include newlines explicitly when building strings
- [zig@0.15] `std.fs.accessableAbsolute` doesn't exist — use `std.fs.openFileAbsolute` with try/catch
- [zig@0.15] `ArrayList.init(allocator)` → `ArrayList.empty`
- [zig@0.15] `ArrayList.writer()` → `ArrayList.writer(allocator)`
- [zig@0.15] `std.os.pid` doesn't exist — use literal 0 for processId in LSP init
- [zig@0.15] `std.fs.File.flush()` doesn't exist — not needed, write is immediate
- [zig@0.15] `std.fs.File.readByte()` doesn't exist — use `file.read()` instead
- [zig@0.15] `json.Value.get()` doesn't exist — use `.object.get()` for object values
- [zig@0.15] `process.Child.kill()` returns `Term`, not void — use `_ = ` to discard
- [zig@0.15] `allocator.dupeZ()` returns `[:0]u8` but argv needs `[*:0]const u8` — use stack buffer approach
- [zig@0.15] `std.posix.Sigaction` is not a struct literal type — initialize fields individually
- [zig@0.15] `std.posix.sigaction()` returns `void`, not error union — no `catch` needed
- [zig@0.15] `std.posix.execveZ()` returns error union directly — use `catch` without `|err|`
- [zig@0.15] `std.posix.sigemptyset()` returns `sigset_t` for signal mask initialization
- [zig@0.16] **CRITICAL: `std.Io.Threaded` does NOT honor user-space deadlines on blocking socket reads** — when a worker thread is parked in `recv()` waiting for data, the main thread's deadline check is dead code. The worker only unblocks when the kernel returns (RST/FIN/error/timeout). To enforce a read deadline on a TCP stream, you MUST set `SO_RCVTIMEO` on the underlying socket fd, OR drive the Io's `select`/`async` with a timeout. Symptom: an "idle timeout" loop never fires when the server stalls without sending RST/FIN. See `src/modules/agent/Agent.zig` callStreaming read loop and the SKIP comment in `call_streaming_test.zig` for the live example.
- [zig@0.16] `std.Thread.Mutex` does NOT exist — `std.Thread` only exposes spawn/join/detach APIs. For a mutex in a `std.Thread.spawn`'d worker, use `std.atomic.Mutex` (a lock-free `enum(u8) { unlocked, locked }` with `tryLock() bool` and `unlock() void`) as a spinlock with `while (!m.tryLock()) std.atomic.spinLoopHint()`. For mutexes held by Io-runtime code, use `std.Io.Mutex` (lock takes `io: Io`). The critical section must be small (a few hundred ns) for the spinlock to be acceptable.
- [zig@0.16] `std.time.sleep(ns: u64)` is removed — use `try std.Io.sleep(io, .{ .nanoseconds = N }, .real)` instead. The `try` is required because `sleep` is `Cancelable!void`.
- [zig@0.16] `std.process.Child.kill(child, io)` returns `void` and blocks until the child dies, then **asserts `child.id == null`**. This means `_ = child.kill(io)` is a no-op AND you cannot call `child.wait(io)` after a successful `kill(io)` — the wait will assert-fail. To track the exit, capture the synthetic Term (e.g. `child_term = .{ .signal = .KILL }`) BEFORE the kill and skip the wait.
- [zig@0.16] **`std.process.spawn` takes `io: Io` as first arg** (not allocator). Signature: `spawn(io: Io, options: SpawnOptions) SpawnError!Child`. The `Child` struct has no `.allocator` field — its handle is owned by the Io runtime. Forgetting `io` and passing an allocator is a common mistake (the allocator will be treated as an Io and the type check fails).
- [zig@0.16] **`std.process.Child.kill(child, io) void` is the all-in-one "terminate + wait + cleanup"** — it sends SIGTERM (or Windows equivalent), blocks until the child exits, sets `child.id = null`, and reaps. You MUST NOT call `child.wait(io)` after `kill(io)` because `wait` asserts `child.id != null` and will panic. Signature: `kill(child: *Child, io: Io) void`. There is no "kill but don't wait" API in 0.16.
- [zig@0.16] **Zig 0.16 has no public `std.posix.socket/bind/listen/accept/connect/recv/send/close`** — they live in `std.os.linux.*` (or `.windows.*`, `.darwin.*`) and return a raw `usize` (success value on success, `-errno` cast to `usize` on failure). Check return against `std.math.maxInt(i32)` to detect errors, then `@intCast` to `i32` for the fd. The `errno()` helper inside `posix.zig` is private.
- [zig@0.16] **`std.Thread.sleep` is gone** — use `std.c.nanosleep(&std.posix.timespec{.sec=..., .nsec=...}, null)`. `std.time.ns_per_ms` and `std.time.ns_per_s` are still available.
- [zig@0.16] **`std.fs.accessAbsolute` is gone** — use libc `std.c.faccessat(AT_FDCWD, path, mode, 0)` directly. The pattern is `if (rc == 0) exists else doesn't`.
- [desktop-app] `nalar-desktop` is the new native webview wrapper at `src/apps/desktop_app/`. It spawns `nalar` as a child process and opens a native webview window (WebKitGTK 4.1 on Linux via manual `extern "c"` + C shim at `platform/webview_linux.c`, WKWebView on macOS via Objective-C++ shim at `platform/macos/nalar_webview.mm`, WebView2 on Windows via C++ shim at `platform/windows/nalar_webview.cpp`). Build: `zig build nalar-desktop`. The Vue webapp is embedded as comptime bytes via the codegen step `zig build codegen:webapp-assets` (which depends on `zig build build:webapp` to run `bun run build` first). Runtime startup: extract assets to `$XDG_RUNTIME_DIR/nalar-desktop-webapp-<pid>/`, spawn `nalar --port <port> --static-dir <webapp-dir>`, wait for `/api/health`, open the webview at `http://127.0.0.1:<port>/`. 21/21 unit tests pass via `zig build test:desktop-app`. The output binary is ~29 MB (includes 4.7 MB of embedded webapp assets + the 17 MB nalarcore link).
- [desktop-app] **Linux WebKitGTK via `@cImport` doesn't work in Zig 0.16** — GLib's `G_GNUC_BEGIN_IGNORE_DEPRECATIONS` macro expands to a C99 `_Pragma("GCC diagnostic push")` that Zig 0.16's libclang can't parse (produces ~7,000 cascading "unknown type name 'diagnostic'" errors). Workaround: skip `@cImport` entirely, declare each GTK/WebKit function manually as `extern "c"`, and add a small C shim file (`platform/webview_linux.c`) that does `#include <gtk/gtk.h>` etc. The C shim is compiled with cc (real Clang) and serves as a header-compile smoke test. This is the only known way to call WebKitGTK from Zig 0.16.

- [VirtualScroller.vue] **FIX: `isScrollable` was a `ref<boolean>` populated by a manual `containerRef.value.scrollHeight` read inside a `ResizeObserver` callback, mount-time setTimeout, and `measureItems` trigger. But `ResizeObserver` only fires when the OBSERVED ELEMENT'S size changes — NOT when content inside it grows. So during streaming, after pagination, or on first item measurement, the observer never fired, `isScrollable` stayed stuck at its initial-mount value (typically `false` from the 0×0 flicker), and the "Load more messages" button in ChatView kept showing in long scrollable chats where the user could have used the scroll path. Fixed by replacing the ref + DOM read with a reactive `computed` derived from `accumulatedHeights[items.length] > containerHeight`. Both sides are reactive refs, so the value updates automatically whenever content or container size changes — no triggers needed. `accumulatedHeights` uses `defaultItemHeight` (200px) for unmeasured items, so the estimate can be slightly off in the milliseconds before `measureItems` runs, but the default matches most chat bubbles closely. The `defineExpose({ isScrollable })` works identically for a `computed` as for a `ref` (Vue auto-unwraps when the parent reads `.value` on the exposed binding). SECOND FIX needed too: the `watch(() => props.items.length, updateAccumulatedHeights)` did NOT have `{ immediate: true }`, so on initial mount the watcher never fired (the items were already present at length 10 when the watch was registered, so the length never "changed" during the watch's lifetime). `accumulatedHeights` stayed at the initial `[0]`, the computed read `accumulatedHeights[10]` which was `undefined ?? 0 = 0`, `0 > containerHeight` is `false`, and the button STILL showed in scrollable chats (user reported "i still see a scroll" / button still visible). Fix: added `{ immediate: true }` so the watcher runs synchronously during setup, populating `accumulatedHeights` with default-height estimates before the first render. THIRD FIX needed too: the parent's `scrollerIsScrollable` was a `computed(() => virtualScrollerRef.value?.isScrollable?.value ?? false)`. This `ref.value.ref.value` chain does NOT reliably establish reactive dependencies in Vue 3 — the component instance proxy returned by a template ref is not a deep-reactive object, so property access on it (`.isScrollable`) is not tracked, and the inner `.value` is on a ref object the parent may have lost identity for. The parent's computed ran once with the initial value and never re-evaluated, leaving it stuck on a stale `false` even when the chat became scrollable. Fix: switch to an event-based pattern. The VirtualScroller emits `scrollability-change` (with `immediate: true` on a `watch(isScrollable, ...)` so the initial value is sent on mount) whenever the value changes. The parent maintains a plain `ref<boolean>` updated by `@scrollability-change="scrollerIsScrollable = $event"`, which the template can react to via standard Vue reactivity. Events have a single, well-defined reactive contract — no proxy-chain dependency tracking involved.** **General lessons: (1) DOM properties like `scrollHeight` are NOT reactive. To make a "is X taller than Y" check reactive, either (a) derive from reactive state (a `computed` over refs/measurements) or (b) wire up an explicit trigger that fires on EVERY relevant state change (a `MutationObserver` on the content/spacers, a watch on the items list, etc.) — `ResizeObserver` alone is not enough because it doesn't watch content changes. (2) When a watcher's source is "already at its initial value at mount time", the watcher never fires unless you pass `{ immediate: true }`. Easy to miss when the data is loaded synchronously by the parent and passed as a prop — the child sees the data immediately, but the "change" event never happens. Always pass `immediate: true` if the watcher's effect needs to run on first render. (3) Don't rely on `ref.value.ref.value` reactivity chains through component instance proxies — switch to events when a child needs to push a value to its parent.**

## Lessons Learned
- **Never build JSON manually** — Use `std.json.Stringify.valueAlloc(allocator, response_struct, .{})` instead of manual string concatenation with manual escaping. Zig's standard library handles JSON escaping properly and the code is cleaner. Example: see `http_response.zig` for response structure definitions and `skills_list.zig` for usage pattern.
- **Unit tests belong in separate files** — Keep implementation (`.zig`) and tests (`_test.zig`) separate. This improves code organization, makes tests easier to find, and avoids cluttering the implementation with test code. Never inline tests in production code.
- **Always register new tests in test_runner.zig** — When creating a new `_test.zig` file, immediately add `_ = @import("path/to/test.zig")` to the appropriate test_runner.zig. This ensures tests are included in the test suite and won't be forgotten.
- **Desktop app: ALWAYS run `bun run build` (NOT `bun run build-only`)** — The desktop app uses TypeScript with strict type checking via `vue-tsc --build`. Running only `bun run build-only` skips type checks and will miss TypeScript errors that cause CI/build failures. Always use `bun run build` to catch type errors before declaring a task complete.
- **TypeScript interface fields must match API response** — When adding a field like `finish_reason` to the API response and using it in ChatView.vue, the interface in `api/index.ts` must also include that field. Otherwise `vue-tsc --build` will fail with "Property 'X' does not exist on type 'Message'" even if the field exists in the actual API response.
- **Never share `[]const u8` slice headers between two `defer`-managed lifetimes** — A `defer free(allocator, slice)` on one lifetime will invalidate any other slice header that still points at the same backing memory. The classic symptom in debug builds is the Zig allocator's `0xAA` free-fill byte pattern showing up in your output, masquerading as a UTF-8/UTF-16 encoding bug. Two safe patterns: (1) build the output directly while the source slice is still alive, then let the source `defer` fire after; (2) if you really need an intermediate list, `allocator.dupe` every entry at append time and explicitly `free` every entry at cleanup time. See `get_skill.zig` and `view_skill.zig` for the before/after; the new regression tests assert `std.mem.indexOfScalar(u8, output, 0xAA) == null` to catch any regression.
- **Deadlines on socket reads in Zig 0.16 must be kernel-level, not user-space** — The "stuck on network drop" bug in `Agent.callStreaming` looked fixable with a user-space deadline loop, but `std.Io.Threaded` parks worker threads in `recv()` so the deadline never fires. The user-space fix (`HttpOptions.idle_timeout_ms` + idle-tracking in the loop) correctly handles the cases where `recv()` returns: TCP RST, FIN, error, or successful read. For the silent-stall case (Wi-Fi drop, half-open TCP, no RST/FIN), you need to set `SO_RCVTIMEO` on the socket via `std.posix.setsockopt(fd, SOL.SOCKET, SO_RCVTIMEO, ...)`. When implementing socket timeouts: get the fd from `req.connection.stream.socket.handle` (or equivalent in the current std.http version), call setsockopt BEFORE the first read, and expect `EAGAIN`/`EWOULDBLOCK` to surface as `error.WouldBlock` from the Io. Test with a fake server that `accept()`s and then sleeps — the deadline MUST fire within the configured window.
- **EventSource auto-reconnect needs explicit wiring** — The browser's native `EventSource` does retry on network-level failures with a 3 s default, but ONLY if the server sends the SSE spec's `retry:` field, and ONLY for some failure modes (4xx/5xx are not retried by the spec). On any non-trivial server (a Zig backend with a `/v1/.../stream` endpoint, an LLM server that streams chunks, etc.), the server doesn't send `retry:`, so a single restart kills the connection permanently. Build a small wrapper (e.g. `helpers/sseClient.ts`) that owns the `EventSource`, the retry timer, and the `visibilitychange` / `online` listeners — and *cancel* the retry timer on `onopen` so a successful reconnect doesn't get killed by a stale timeout. The two latent bugs in the previous hand-rolled `setTimeout(reconnect, 5000)` pattern are: (1) the timer leaks on unmount (no reference held → no `clearTimeout` possible), and (2) a *second* transient error can fire the original timer, which calls `close()` on a *working* connection. The wrapper pattern fixes both: timers are closure-scoped to the client, `close()` cancels them, and `onopen` resets the attempt counter. See `docs/sse-reconnect-plan.md` for the full design.
