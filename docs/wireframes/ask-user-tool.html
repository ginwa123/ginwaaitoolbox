ask_user — agent tool wireframe

The agent stops mid-task, asks the human a question with selectable options and/or free text, and the turn ends. When the human answers, the answer is written back as the tool result and a new run continues the conversation.

Plan: docs/superpowers/plans/2026-09-16-agent-tool-ask-user.md · Card lives inline in the transcript, exactly where every other tool card lives. The question is a persisted row, so it survives a reload and can be answered at any time — there is no timeout and nothing is kept waiting in memory.

4 Flow

agent calls ask_user→ gate: unattended / sub-agent? → unavailable, same run → INSERT session_pending_question (Migration 087) → tool returns <status>pending</status> immediately
handle_tool finishes the batch (every tool_call already has its row) → BREAK — persist finish_reason=awaiting_user, delete worker → card waits, session idle, no timeout
human picks staging→ POST /api/llm/session/:id/answer→ UPDATE question row→ REWRITE the tool-result row in place (+ llm_full → card flips) → emit_run_agent skip_initial_queue_message=true → new run resumes
order
matters The row rewrite must land before the resume run starts. Placeholder tool rows are is_feed_to_llm = 1, so a run that starts first would hand the model <status>pending</status> and it might guess. If the rewrite fails, the endpoint errors and leaves the row pending so Retry is safe.

Nothing new on the wire

event: llm_full        ← the standard tool-result row

{ "tool_name": "ask_user",
  "tool_call_id": "call_abc",
  "role": "tool",
  "content": "<tool><name>ask_user</name>
              <parameters>{ …args… }</parameters>
              <success>true</success>
              <data><ask_user>
                <status>pending</status>…" }

No new named SSE event, so nothing to add to additionalEventTypes and no browser-side silent-drop risk (the PR #291 bug class). The answer rewrites the same row id, so the open chat patches the card through the existing in-place llm_full path — and a reload just re-fetches history.

Why the loop can break safely

handle_tool Phase 1
  → 1 assistant row (tool_calls=[ask_user])
  → 1 role=tool row  per tool_call   ← ALWAYS
     (is_feed_to_llm = 1, tool_call_id set)

so a break leaves a MATCHED chain:
  assistant(tool_calls) + tool(result)

Which is exactly what a normal completed
tool turn looks like — the next run's
payload builder replays it verbatim.

Verified in handle_tool.zig:513-566: the placeholder insert loop has no filter, so even an unknown tool gets a row. There is no orphaned tool_calls entry to trip the OpenAI/Anthropic/Responses builders.

What ask_user does to the turn

The call arrives as a tool call, so the LLM turn's finish_reason is tool_calls — then handle_tool completes the batch and the workflow breaks, persisting finish_reason = awaiting_user on the assistant row (a new value in the FinishReason enum; nothing switches exhaustively on it, and last_finish_reason is display-only). The worker is deleted, the session goes idle, and the composer becomes usable again.

6 Decisions locked in review

QuestionAnswer
Does ask_user end the turn?Yes — the loop breaks. No parked thread, no in-memory wait, no timeout.
Ephemeral or persistent question?Persistent — and this design makes that free: the question is just a row you answer later.
How does the card know the question?From the tool-result row itself (args + <status>). No side map, no rehydration call.
How does the answer get back?The tool row is rewritten in place, then emit_run_agent(skip_initial_queue_message=true) starts a new run.
Where does the answer appear?Inside the card only — not as a separate user bubble.
What does Skip mean?The run continues; the model is told not to guess and to stop that line of work.
What if you type instead of answering?Resolved as abandoned, then your message runs. Never a dead end.
Which modes get the tool?All modes by default — chat, agent items, kanban items.
What if nobody is there?Unattended run → unavailable in the same run. Otherwise the question simply waits.
