Wireframe — the 3 footer buttons of the Kanban task dialog

Task task_1790616305483_5  ·  Component src/apps/desktop/src/components/kanban/KanbanTaskDetail.vue:1812-1907
Plan docs/plans/2026-09-29-kanban-task-detail-3-buttons.md

The sticky action row at the bottom of the New-task / Task-details panel: Cancel  ·  Create task  ·  ▶ Create task & run agent. In edit mode the third button is ▶ Start agent and the second reads Save. Colours below are the real tokens from src/apps/desktop/src/style.css (--semantic-card-bg #1D1C19, --color-border #282727, --semantic-text-muted #a6a69c, --semantic-text-dim #7a8382, primary linear-gradient(135deg,#8992a7,#8ba4b0) on #181616 text). Buttons are drawn at their real size (px-3 py-1.5 text-sm rounded-lg → 28 px tall here). Nothing is implemented yet — this is the design review artefact. Hover a drawn button to see the hover state the proposal adds; hover nothing on the "as shipped" row, because today there is none.

Recommendation

Option A — "promote the run". Reorder to Cancel · Create task · ▶ Create task & run agent, give the run button the gradient, drop the border off Cancel, and add the four universal fixes (hover / focus ring / wrap / per-button pending label).

Why: 22 of the 24 footer rows in this codebase put the primary rightmost; this one is one of only two that doesn't. The fix is a reorder, not a new primitive. It also makes the row agree with the keyboard — pressing Enter in the name field already runs the agent (KanbanTaskDetail.vue:842-848), so today's visual default ("create only") contradicts the actual default ("run"). A third option that costs nothing and is not even a design change is the fallback if you want minimal churn.

Also worth doing regardless of which option you pick: F2 (hover + focus ring — three buttons with zero pointer affordance is the cheapest defect here) and F1 (only the pressed button says Creating…). Those two are pure wins with no layout risk.

defects, in descending order of how much they cost the user
  1. The primary is not rightmost. Create task (gradient) sits in the middle with a secondary to its right. The eye lands on the right edge, which is the least important action. 22 of 24 footer rows in this app put the primary last; the only other inversion is RoutineView.vue:566-592.
  2. Cancel and the run button are pixel-identical. Same border: 1px solid var(--color-border), same color: var(--semantic-text-muted), same size. "Discard my work" and "create the task and have an agent start working" are presented with the same weight. There is no 3-step hierarchy, only a 2-step one, and the middle rung is missing.
  3. Which button did I press? Unknowable. isCreating is a single host flag (KanbanView.vue:1197 createBusy) driving both create buttons, so either click flips both labels to Creating… (source :1845 and :1870). The round-trip includes image base64 encoding, so this can last seconds.
  4. No hover, no focus ring, on any of the three. The classes are transition-all duration-200 with nothing to transition. The house hover model is hover:opacity-80 and it is used on the Back button at :1162-1181 — 20 lines above this one. Keyboard users get the UA default ring, which style.css:110-120 deliberately avoids restyling.
  5. The keyboard default contradicts the visual default. handleEnterKey (:842-848, bound to the name input) runs the agent in create mode — never a plain create. So the fastest path in the dialog is the one that isn't styled as the default.
  6. Two long labels with the same first two words. "Create task" and "Create task & run agent" side by side is a diff, not a menu. A glance can't tell which is richer.
  7. No wrap. The footer is flex with no flex-wrap and no responsive prefix. Below roughly 480 px of panel width the row overflows its own container instead of reflowing.
  8. The subtitle argues with the primary. "Optionally start an agent on it right after" (:1206-1212) frames running as the extra step, while the button row spends the same visual weight on it.

the argument for promoting the run
  • Enter in the name field already calls handleRunAgent() in create mode (:843-844). The primary should be the thing the keyboard already does.
  • "Create the task, I'll start the agent myself" is the rarer intent in an agentic board — the board exists to hand work to agents.
  • It costs nothing to revert: keep Create task as the primary and move it last, and you're back to a correct house-conforming row.
the argument against
  • Gradients on a button mean "this commits something". Making the more consequential action (it starts a worker) the loudest one is a real judgement call.
  • The subtitle copy says "Optionally start an agent on it right after" — under Option A that sentence is backwards and should flip to "…or start an agent on it right away."

trade-off
  • For: footer becomes the same shape as the other 22 dialogs, and the user makes the "run or not" decision while reading the form rather than at the last second. The ▶ glyph, the create-and-run emit, and both handlers survive untouched — it's a re-plumbing, not a rewrite.
  • For: the enabled/disabled logic collapses. Today both buttons gate on the same canCommitCreate; a switch is never disabled, so isCreating only has to lock one button.
  • Against: a switch says "this is the state of the task", but "run once" is an event, not a state. It's the wrong control type and the switch may read as "unattended will start it later".
  • Against: kanban-task-detail-create-and-run would vanish from the DOM — the same ~30-site testid problem as Option B, and a Playwright hard-assert at kanban_profile_select_ui_test.py:412-416 fails outright.
  • Against: biggest behaviour change of the four. Enter must now consult the switch or it silently does the wrong thing.
If the real complaint is "this footer is too busy", this is the honest answer. If the complaint is "I can't tell which button is the main one", Option A is enough.

7 — The four universal fixes apply to A, B, C and D

F1 · only the pressed button says "Creating…"

today — the user cannot tell which one they hit
isCreating = true, clicked "Create task"
Cancel Creating… Creating…
Two identical "Creating…" labels, side by side, and no spinner on either. Both buttons sit at opacity: .5 because disabled:opacity-50 applies to the one that wasn't clicked too.
proposed — press, lock, explain
pressed "Create task"
Cancel Creating… Create task & run agent
pressed "▶ Create task & run agent"
Cancel Create task Starting…
The pressed button spins and says what it is doing; the sibling keeps its label so the row doesn't turn into two identical words. Both stay disabled — that guard is the double-submit protection and it must not be weakened.
how to implement without touching the host contract

The dialog is fully prop-driven today: isCreating = computed(() => props.creating === true) (:806) and the host owns the single createBusy ref. The minimal version is one local ref set inside the two handlers (pendingAction: 'create' | 'create_and_run' | null, cleared when props.creating goes back to false). The label becomes isCreating && (pendingAction === 'create_and_run' || pendingAction === null) ? 'Starting…' : … — note the || pendingAction === null fallback, which preserves today's behaviour whenever the host raises creating through some path the dialog didn't initiate.

Test consequence: none. creatingGuard.spec.ts mounts with creating: true and never clicks, so pendingAction is null and both buttons still read Creating… — the existing assertions at :92-93, 135-136, 159-160 keep passing. You add a new spec for the click case rather than editing the old one. Keeping the null fallback is what makes this free; drop it and you break 5 assertions.

F2 · hover + focus-visible on all three cheapest fix here

model, copied from the house style
  • Hover — hover:opacity-80. The whole app's hover model; there is not one hover:bg-* on a button anywhere. Used by the Back button at :1162-1181, 20 lines above the footer.
  • Focus — focus:outline-none focus-visible:ring-2 ring-offset-2 ring-[--color-blue]. Deliberately focus-visible, not focus, so a mouse click doesn't leave a ring. focus-visible:ring-2 appears exactly once in the app today (KanbanToolsPanel.vue:339), so this would make the footer the second — a small, defensible precedent, not an invention.
  • Disabled — keep disabled:opacity-50 disabled:cursor-not-allowed, and make sure hover:opacity-80 is suppressed on disabled buttons (disabled:hover:opacity-50), or a locked button still looks clickable.

Try it: Tab through the row (real focus ring), then hover each button. On the "as shipped" row in §1 the same two actions do nothing at all.

F3 · let the row wrap

the change

Add flex-wrap: wrap (plus row-gap if you want the two lines to breathe) to the footer container at :1813. One class. The container is flex justify-end gap-2 shrink-0 sticky bottom-0 inside a w-full card, so wrapping is safe — the card has no max-h and the host owns the scroll.

F4 · make Cancel a ghost button

the change

Drop border: 1px solid var(--color-border) from the Cancel button and take its text from --semantic-text-muted #a6a69c down to --semantic-text-dim #7a8382. A border on a button means "this is one of the choices you make"; Cancel isn't a choice, it's the absence of one. This is the single change that stops Cancel from being visually identical to the run button, and it works in every option including D.
