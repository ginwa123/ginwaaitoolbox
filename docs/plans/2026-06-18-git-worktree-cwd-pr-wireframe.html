NEW Clicking the chip opens a dropdown with three actions. The dropdown mirrors the existing "Default" profile-picker pattern (absolute bottom-full mb-2 left-0). Closing happens via:
  • Click outside the dropdown
  • Selecting any action (the parent closes the menu via v-if)

Action behaviors:
  • 🔀 Create a PR — direct API call (POST /api/git/pr); opens the CreatePrDialog (State 4).
  • 📁 View in folder — copies the worktree path to the clipboard (v1); future plan will open a folder-explorer modal.
  • 🗑️ Clear worktree — shows a confirm() dialog; on accept, sends a system message to the LLM asking it to call set_git_worktree(clear=true). The LLM does the cleanup; the SSE event updates the chip.

State 4: "Create a PR" dialog (NEW — pre-filled form)

🔀 Create a pull request

NEW The dialog pre-fills on mount from GET /api/git/worktree/info:
  • Base branch — auto-detected by trying origin/main → origin/master → origin/develop. User can override.
  • Title — the worktree's last commit subject (the user just typed this in the chat — it should match what they're submitting as a PR).
  • Body — a markdown summary with the diff shortstat (3 files changed, 142 insertions(+), 23 deletions(-)) and commit count.

Auto-fill button (NEW, top-right of the dialog header): ↻ Auto-fill re-fetches GET /api/git/worktree/info?path=...&base=<current_base> and overwrites BOTH the title (from the latest commit subject) and the body (from the diff against the current base branch value in the input). Useful for:
  • (a) The user changed the base branch — body now shows the diff against the new base.
  • (b) The worktree has new commits since the dialog was opened (e.g. LLM kept working).
  • (c) The user manually edited the title/body and wants to revert to the auto-generated version.
The button shows a small spinner during the request and is disabled while submitting (no race with the Create PR button).

Submit: calls POST /api/git/pr with the form values. The backend runs gh pr create --base <base> --title <title> --body <body> in the worktree path. On success, the dialog emits pr-created with the PR URL → the parent closes the dialog and window.open(url, '_blank') opens the PR.

Error cases (all surface inline in the dialog):
  • gh not installed → 500 with hint "is the gh CLI installed and on PATH?"
  • gh not authenticated → verbatim gh stderr
  • Branch not pushed to origin → verbatim gh stderr ("no commits between origin/main and worktree/feature-x")

State 4b: User changed base branch + clicked "↻ Auto-fill"

🔀 Create a pull request

NEW Scenario: The user changed the base branch from main to develop and clicked the ↻ Auto-fill button. Here's what happened:
  1. The button shows a spinner (violet color to indicate in-flight request).
  2. The frontend calls GET /api/git/worktree/info?path=/abs/.worktrees/feature-x&base=develop.
  3. The backend re-computes commits_ahead and diff_summary against origin/develop instead of the auto-detected default.
  4. The frontend overwrites title.value with the latest commit subject (unchanged in this example) and body.value with the new diff summary (now shows 5 files changed, 187 insertions(+), 41 deletions(-) instead of 3 files, 142).
  5. The base branch input keeps the violet border briefly to show "this is what was just refreshed against" (vanishes after 1s).

Why use the CURRENT base (not the auto-detected default)? Because the user explicitly typed a different base, and they want the body to reflect the diff against that base — not the original auto-detected one. This is the key value-add of the Auto-fill button: it respects the user's input rather than reverting to the default.

REVERT After "Clear worktree" the LLM calls set_git_worktree(clear=true):
  1. The worktree directory is removed (via git worktree remove --force)
  2. The DB row's git_worktree_cwd is set to NULL
  3. An SSE event fires on /sessions/stream with git_worktree_cwd: ""
  4. The chip reverts to the original branch (main), no 🌳 suffix, no caret — matches State 1 exactly.

Caveat (documented in the plan): the active ChatView doesn't currently subscribe to /sessions/stream, so the user may need to refresh the page (or trigger a loadChatHistory) to see the revert. This is a v1 limitation; the follow-up plan wires real-time updates.

What stays the same

  • The chip position in the status bar (between "Default" profile picker and "Tokens" indicator).
  • The chip's overall look (same colors, border, padding, font size).
  • The ●/✓ status indicator (orange for dirty, green for clean) — but now reflects the worktree's working tree, not the session's.
  • The 30-second polling interval for git status updates.
  • Behavior when no worktree is bound — chip stays non-clickable, identical to today.
