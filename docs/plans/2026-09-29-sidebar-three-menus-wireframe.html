Wireframe — the three left-sidebar menus: New Chat · Recent · Projects

Task task_1790616057649_4  ·  Companion plan docs/plans/2026-09-29-sidebar-three-menus.md  ·  Predecessors 2026-09-22-revamp-workspace-ui-dropdown-projects, 2026-09-27-sidebar-new-chat-default-project
The sidebar has exactly three menus and every screenshot of it shows the same complaint: they are hard to tell apart. Recent and Projects render identical rows for the same chats, Projects cannot be scanned because a kanban looks like an agent, and the numbers next to each project are not what they claim. This wireframe gives each of the three menus one job — Resume, Inventory, Act — and makes the two row types visually distinct.
Colours, weights and geometry are the real tokens. The 210 px sidebar is drawn narrow, as in the 2026-09-27 wireframe, so the header/action/row geometry is legible at this size. Nothing here is code — every path:line is a pointer to the current implementation the drawing is arguing with.

The overlap is not a bug that crept in

A project child is a chat. Migration 052 dropped workspace_item_tasks.session_id because task.id is the session id. And the RECENT list is workspace-scoped by unioning in exactly those task ids:

scopesrc/agentic_loop/workspace_scope.zig:89-91
querysrc/agentic_loop/llm_history.zig:381
FROM sessions s … s.id IN (…)
schemasrc/migrations/migration.zig:1048

So every task whose chat has been run appears twice — once under RECENT, once nested under its project. Duplication here is intentional and fine. What is missing is any way to tell the two copies apart, which is the whole of §3.

Note what is not wrong. Duplicating a chat in a recency list and an inventory is correct — VS Code, Slack and Linear all do it. The defect is that both lists draw the same row (4 px bullet, name, right-hand meta), so the second copy carries no information: you cannot tell whether a RECENT row is the project child you expanded ten pixels below it, or a loose chat. §3 fixes the row, not the duplication.

2 — Nine defects, each with the line that proves it

Diagnosed 2026-09-29 — none of these is a taste preference
  1. P1 · The two menus are indistinguishable. A project child and a RECENT row draw the same markup. There is no type, no parent, no affordance that differs. WorkspaceItemTaskRow.vue:158-325 vs ChatsList.vue:969-1058.
  2. P2 · No item-type glyph anywhere. Every project row is ▶ plus a name. Kanban, agent, design and routine are told apart only by what happens when you click. WorkspaceItem.vue:617-633 — and there is no icon map in the codebase to draw one from.
  3. P3 · The numbers are lies. The 119 is item.tasks.length — rows paged in at 10 per page, not a total. WorkspaceItem.vue:634-639, stores/workspaces.ts:915. The backend computes no COUNT at all: http_response.zig:618 sets .count = tasks.len, i.e. page length, and the client never surfaces it. The 9 is workspace.items.length, ignoring the server's items_count. ProjectsList.vue:391-394
  4. P4 · Three always-on buttons per child row. Pin, rename, delete sit at opacity-60 on every row, always. Ten children is thirty controls competing with the names. WorkspaceItemTaskRow.vue:264-317.
  5. P5 · Children are unlabelled. Under AGENTIC BASIC, seven consecutive rows read New Chat. Nothing says which parent they belong to, or when they ran.
  6. P6 · Two independent scrollers. RECENT is a resizable pane pinned to 40 % (sidebar.ts:14); PROJECTS takes the remainder. Expanding a ten-child project scrolls RECENT out of view, and vice versa.
  7. P7 · No search, and none is coming. Deliberately removed in the v2 revamp — ProjectsList.vue:84-85 and :411 — so with nine projects and one hundred-plus children there is no way to find anything but scrolling.
  8. P8 · RECENT has no empty state. The only branch is a Loading… label; chatsTotal === 0 renders nothing at all. ChatsList.vue:1061-1063. PROJECTS has two proper empty states; RECENT has zero.
  9. P9 · No way out of a big project. Android ships a See all chats › button for exactly this (2026-09-27-android-sidebar-projects-wireframe.html, decision 3). Desktop has only a Load more button inside a pane you can accidentally resize away.
Two more, smaller, that the drawings below fix as a side effect: P10 — section collapse is localStorage-only, never the URL (stores/sidebar.ts:5,68-108), which the repo's URL-sync rule forbids. P11 — the worker-running indicator is a bare ring, so it reads as a stray radio button; the only unambiguously labelled state in the sidebar is the one nobody can read.

6 — Row anatomy: two row types, three states, one active rule

The type system this proposes

Three visual grammars, each doing exactly one job. Nothing may render two grammars at once.

RowLeadingSecond lineRight
Projectglyph ▦ 🤖 🎨—⋯ on hover
Chat4 px bulletbreadcrumb (RECENT only)time · ⋯
Sectioncarate ▼—count removed, + kept

The glyph is the project row's identity — so the chevron moves to the right of the name, or the glyph takes the chevron's place and expansion is indicated by the whole row. What must not happen is today's arrangement, where ▶ means expands on a kanban that has no children to expand.

The active rule, which is still a TBD in the repo

A project row is a filter — it expands in place and never navigates. A chat row is a destination — it navigates. That rule is already written down in the Android wireframe's tap-semantics table; this section applies it to the desktop, where nothing states it.

The active row gets a 2 px left accent bar plus a fill, derived from the URL — never from a store flag. docs/SPEC.md:971 has been sitting open on exactly this since 2026-08-06:

#TBD feat(sidebar): URL-driven single-active state — sidebar components derive "active" from useCurrentMainView() (route.query), not store flags; 2px violet left accent bar on item + page rows

§5 draws the aqua dot on AGENTIC BASIC for exactly this reason: with /app/{ws}/projects/{pid}/chat/{tid} in the URL, the sidebar must open that project and light that child without the user having expanded anything.

8 — Search: the decision this wireframe deliberately reopens

This contradicts a decision the human already made

The v2 sidebar revamp removed search on purpose. It is not an oversight and it is not commented as one — it is stated:

ProjectsList.vue:411  "Search removed (v2 sidebar UX) — every project is listed."
ProjectsList.vue:84-85  "Sidebar shows every project — the header search filter was removed."

The argument for putting it back is §2: the same workspace holds nine projects, one of them with a hundred-plus children, and after this wireframe removes the number badges the tree is the only affordance for finding anything. The argument against is real too — a filter that hides a project is a project you cannot see exists, and the tree is nine rows tall.

This is a question, not a proposal with a fait accompli. Q1 in §10. If the answer is no, the tree survives as drawn and only the URL work in §7 lands.

10 — Decisions this wireframe depends on

Proposing
  1. D1Duplication stays; the rows diverge. RECENT keeps every task-backed chat. It gains a breadcrumb; a project child never gets one. Rejected: de-duplicating RECENT against the tree — the tree is collapsed most of the time, so "already visible" is not a property you can compute.
  2. D2RECENT is a 5-row timeline with See all ›. The resizable pane and the Load more row inside it are deleted. Rejected: keeping the 40 % pane — it is the second scroller in §7.
  3. D3Projects get the docs/tabs.md:148 glyphs, fail-soft to ▤. Rejected: the Android wireframe's ▦ ◍ ↻ ✎ ▤ set — a second vocabulary for the same six types is worse than reusing the one the tab strip already ships.
  4. D4All row count badges are removed. The honest count moves to See all N chats › and only once the backend returns a real total. Rejected: keeping items_count on the section header — it is server-true but the section already lists every row.
  5. D5Row actions become hover-revealed ⋯ on both menus; the existing right-click menu is unchanged and gains Shift F10. Rejected: keeping pin/rename/delete always-on — thirty controls for ten rows.
  6. D6One scroller for the nav. chatsHeight and its drag handle are deleted; section fold state moves into the route as ?nav=. Rejected: keeping the resize handle — nothing in the app resizes a pane by dragging, and this one is not even reachable by keyboard.
  7. D7The active project auto-expands from the URL and the active chat row gets a 2 px accent bar. This closes docs/SPEC.md:971.
  8. D8RECENT gets a real empty state — "No chats yet — press ⌘N to start one." Rejected: the current silent Loading….
  9. D9The running indicator is labelled ◌ run. Rejected: the bare ring, which is the only state in the sidebar a user cannot read.
  10. D10New Chat gains ⌘N and a ▾ split. Weight, colour and the top-24 chevron are untouched — the 2026-09-27 decision holds.
Still open — the reviewer's call
  1. Q1Does Projects get a filter box? §8. This reopens a deliberate 2026-09-22 removal. Recommendation: yes — nine projects and a hundred-plus children with no other affordance. But it is the human's decision, and the wireframe stands without it.
  2. Q2Does the project row keep a chevron at all? §6 draws ▶ beside the glyph, but a kanban and a routine have no children, so their chevron is a dead control. Options: hide it for childless types, or drop it and indicate expansion on the row. Recommendation: hide it — a control that cannot do anything should not be drawn.
  3. Q3Does a project child keep its own time pill? §5 draws one, matching RECENT. The data is there (updated_at on the task row) but it is a second number competing with the name inside a 210 px rail. Recommendation: keep — the seven identical New Chat rows are exactly the case where a timestamp is the only thing that distinguishes them (P5).

Nothing in §1–§7 depends on an answer here. Q1 gates only the search box; Q2 and Q3 change one glyph and one label.

11 — What it costs, and what it buys back

Backend — one small addition

See all N chats › needs a real N. Today src/http_handlers/tasks_list.zig contains no COUNT(*) at all; the response carries .count = tasks.len — the page length — and api/index.ts:722-726 does not even return it to the caller.

The change is a COUNT alongside the existing cursor-paginated SELECT, surfaced as a distinct total field. Not in this wireframe — it is its own card, and until it lands the number does not appear at all (D4).

What gets deleted
  • sidebarStore.chatsHeight + its drag handle and the MIN/MAX clamp (stores/sidebar.ts:14).
  • The items.length count on the PROJECTS header and the tasks.length badge on every project row.
  • Two localStorage keys, replaced by ?nav=.
  • The 3 always-on SVG buttons on every child row, collapsed into one ⋯.

No route is removed. /app/{ws}/projects/{pid}/chat/{tid} and /app/{ws}/chat/{sid} both stay — a project child and a loose chat are different URLs today and stay different.

12 — How this gets verified

This is a wireframe, so nothing here runs yet. When it is implemented, the rules the repo already enforces apply in full:
  • Not by starting a server and curling it. Every route and wire payload graduates to tests/functional/harness.py — a free port in 8080–8199, never 8081, and an isolated HOME tmpdir.
  • Every view switch lands in the URL, covered by a mount-with-query spec asserting the restored view and a click spec asserting the query value — the SidebarDiffPanel.tabs.spec.ts pattern.
  • Route order is a live trap. matchRoute walks routes in registration order (kabelweb src/server/router.zig:182), so a new literal route registered after a :param route is captured by the param. A unit test on the composable will not see it.
  • One spec per decision. D4's "no count" and D7's "active row from the URL" are both assertions that are cheap to write now and expensive to notice missing later.

13 — Explicitly not in this wireframe

  • The workspace header. ▾ name Settings Logout is settled by the 2026-09-22 revamp and is drawn unchanged. It is the fourth menu and it is out of scope.
  • Per-mode sidebars. There is exactly one Sidebar.vue shared by every mode; nothing here proposes splitting it. (The appbar inconsistency across modes is a separate card.)
  • Any new route shape. Existing URL contracts stand.
  • Drag-to-reorder of projects and the Add Project row, which is still disabled "Coming soon".
  • Folder file listing — a folder project expands to its chats like every other type.
  • The Android drawer. Everything here should be mirrored there, but the drawer is its own card.
