# Desktop Webview App — Design

**Date:** 2026-06-10
**Status:** Approved
**Owner:** ginwa
**Implementation Plan:** `docs/superpowers/plans/2026-06-10-desktop-webview-app.md` (next step)

---

## Overview

Wrap the existing Vue 3 webapp (`src/apps/desktop`) in a native window driven by a new Zig binary (`nalar-desktop`). The wrapper spawns the existing `nalar` server as a child process, waits for it to be healthy, opens a webview pointed at it, and tears the server down on window close.

The webapp itself is unchanged. The existing `nalar` server is unchanged. The only new artifact is `bin/nalar-desktop` (plus a tiny platform-shim file on macOS and Windows).

**Result:** a single-binary install (`nalar-desktop`) that, when launched, gives the user a desktop window showing the existing nalar UI.

## Architecture

### Process model (one run)

```
┌─────────────────────────────────────────────────────┐
│                  nalar-desktop (Zig)                │
│  ┌─────────────────────────────────────────────┐    │
│  │ 1. parse args (--port 0, --nalar-path …)    │    │
│  │ 2. locate nalar binary                      │    │
│  │ 3. allocate free port for nalar             │    │
│  │ 4. spawn: nalar --port <port>               │    │
│  │ 5. wait for GET /api/health → 200           │    │
│  │ 6. create native webview window             │    │
│  │    └─ loadURL: http://127.0.0.1:<port>/     │    │
│  │ 7. run event loop (GTK / NSApp / Win32 msg) │    │
│  │ 8. window closed → kill nalar, exit         │    │
│  └─────────────────────────────────────────────┘    │
└────────────────────────┬────────────────────────────┘
                         │ spawn
                         ▼
                ┌──────────────────┐
                │   nalar (Zig)    │  same monorepo
                │   port = <rand>  │  existing server
                │  /api/* + /api/  │  unchanged
                │   health         │
                └──────────────────┘
```

### Code layout (new files)

```
src/apps/desktop_app/                  ← NEW directory (Zig, not Vue)
├── main.zig                           ← entry point, CLI parsing, lifecycle
├── subprocess.zig                     ← spawn nalar, healthcheck, kill on exit
├── webview.zig                        ← Webview interface + comptime dispatch
├── platform/
│   ├── linux.zig                      ← WebKitGTK 4.1/6.0 + GTK loop (all in Zig)
│   ├── macos.zig                      ← calls into platform/macos/nalar_webview.mm
│   └── windows.zig                    ← calls into platform/windows/nalar_webview.cpp
├── platform/macos/
│   ├── nalar_webview.mm               ← Objective-C++ shim
│   └── webview_c.h                    ← shared C header
├── platform/windows/
│   ├── nalar_webview.cpp              ← C++ shim
│   └── webview_c.h                    ← shared C header
├── config.zig                         ← window size, title, icon, User-Agent
├── port.zig                           ← free-port allocator
├── cli.zig                            ← CLI argument parsing
└── embedded/                          ← gitignored, populated by build
    └── webapp_assets.zig              ← generated by build.zig, lists dist/ files
```

```
build.zig                               ← MODIFY
  + step "build:webapp"        → bun run build in src/apps/desktop
  + step "build:desktop-app"   → compile nalar-desktop, depends on "build:webapp"
  + step "run:desktop-app"     → b.addRunArtifact(desktop_exe)
  + step "test:desktop-app"    → unit tests on the testable slice
  + install step copies nalar + nalar-desktop to zig-out/bin/
```

### Startup data flow

1. `main.zig` parses CLI:
   - `--port <u16>` — port to bind nalar on (default: 0 = auto-pick free)
   - `--nalar-path <path>` — explicit path to nalar binary (for testing)
   - `--window-size WxH` — default 1280x800
   - `--title "Nalar"` — window title
   - `--user-agent "NalarDesktop/1.0"` — User-Agent override
   - `--icon <path>` — window icon (nullable)
   - `--smoke-test` — headless mode for CI: open, wait 2s, exit 0
2. `port.zig` opens a listening socket on `:0`, reads the OS-assigned port, closes the socket (port may be reused, but the next bind in nalar is fast enough that collisions are rare; we add a retry on `EADDRINUSE`).
3. `subprocess.zig` locates the `nalar` binary (resolution order: `--nalar-path` → same dir as self → `$PATH`).
4. `subprocess.zig` spawns `nalar --port <port>` with `stdin=.ignore`, `stdout=.pipe`, `stderr=.pipe` (we capture stderr for diagnostics).
5. `subprocess.zig` polls `http://127.0.0.1:<port>/api/health` every 100ms up to 10s.
6. On 200, `webview.zig` calls `platform.<current>.createWindow(config, url)`.
7. The platform impl creates a window with the config, registers an asset-intercept handler that serves the embedded `webapp_assets`, then loads `http://127.0.0.1:<port>/` (which is the Vue app, served by nalar as static files).
8. `main.zig` calls `webview.runEventLoop()` — blocks until the window closes.
9. On window close: SIGTERM nalar, wait up to 2s, SIGKILL if still alive, exit 0.

### Locating the `nalar` binary at runtime

Resolution order, first wins:
1. `--nalar-path` CLI flag (for testing with a custom build)
2. `nalar` next to `nalar-desktop` itself (resolved via `/proc/self/exe` on Linux, `_NSGetExecutablePath` on macOS, `GetModuleFileNameW` on Windows)
3. `nalar` in `$PATH` (`std.process.findInPath`)

`zig build install` puts both `nalar` and `nalar-desktop` into `zig-out/bin/`, so option 2 is the default for both `zig build run` and packaged installs.

## The shared Webview interface (compile-time dispatched)

All three platforms implement the same C ABI. Linux can call WebKitGTK directly from Zig via `@cImport`. macOS/Windows each ship a small native shim file (`.mm` / `.cpp`) that exposes the C ABI.

```c
// webview_c.h — shared header
typedef struct nalar_webview nalar_webview;

typedef struct {
    const char* title;
    int width, height;
    int min_width, min_height;
    bool resizable, maximizable, minimizable;
    const char* user_agent;
    const char* icon_path;            // nullable
    // Asset handler: webview calls this for every request the page makes
    // (intercepted, never goes to the network for app:// URLs).
    // The shim is given a flat array of {path, content, mime} entries.
    const nalar_webview_asset* assets;
    size_t asset_count;
} nalar_webview_config;

nalar_webview* nalar_webview_create(const nalar_webview_config* cfg, const char* url);
void nalar_webview_run(nalar_webview* wv);    // blocks until window closed
void nalar_webview_destroy(nalar_webview* wv);
```

Zig side:
```zig
pub const Webview = opaque{};

pub const Config = extern struct { /* mirrors nalar_webview_config */ };
pub const Asset = extern struct {
    path: [*:0]const u8,
    content: [*]const u8,
    content_len: usize,
    mime: [*:0]const u8,
};

extern "c" fn nalar_webview_create(cfg: *const Config, url: [*:0]const u8) ?*Webview;
extern "c" fn nalar_webview_run(wv: *Webview) void;
extern "c" fn nalar_webview_destroy(wv: *Webview) void;
```

The webview shim is given the full asset table and intercepts every request the page makes — for `app://...` URLs, it serves the asset from the in-memory table; for `http://127.0.0.1:<port>/...` URLs, it passes through to nalar (SSE and `/api/*` calls all go this way). Wait — this is wrong: if we intercept `http://...`, we break SSE and the API.

**Corrected approach:** the webview loads `http://127.0.0.1:<port>/` directly. The nalar server is the source of truth for both the static webapp (the index HTML is served by nalar, and nalar also serves the asset files referenced by it) AND the API/SSE. The webview's job is just to be a window.

This means **the embedded Vue dist/ must be served by nalar, not by the webview**. We need a way to tell nalar where the embedded assets live at runtime. Since they're embedded in the nalar-desktop binary, nalar doesn't know about them.

**Resolution:** nalar already supports a `--static-dir <path>` flag... actually no, it doesn't yet. We have two options:

- **Option α (recommended):** Add a small static-file route to nalar. The desktop app calls nalar with `--static-dir <tmp-dir>` after extracting the embedded assets to a temp dir on first run. Adds extraction code to the desktop app, but the temp dir is per-user, cleaned up on exit, and well-scoped.
- **Option β:** Have nalar grow a `--embedded-assets` flag that takes a base64 tarball. nalar extracts and serves it. Single-binary distribution becomes possible. Adds more code to nalar.
- **Option γ (rejected):** Make nalar serve from a `static/` directory that's expected to exist on disk. Desktop app extracts to `<data-dir>/nalar/webapp/`. Persistent across runs, no re-extraction, but needs cleanup logic.

We pick **Option α** for v1. The temp-dir extraction is ~30 lines of code in `subprocess.zig` and keeps the nalar side clean. v2 can revisit Option β if single-binary distribution becomes a hard requirement.

**Updated startup flow:**
1. `main.zig` extracts embedded Vue dist/ to a per-user temp dir (e.g., `$XDG_RUNTIME_DIR/nalar-desktop/webapp-<pid>/` on Linux, `$TMPDIR/nalar-desktop-webapp-<pid>/` on macOS, `%TEMP%\nalar-desktop\webapp-<pid>\` on Windows)
2. `subprocess.zig` spawns nalar with `--static-dir <temp-dir>` (or whatever flag we add to nalar to enable static serving)
3. nalar serves the static files at `/` (index.html) and `/assets/*`
4. Webview loads `http://127.0.0.1:<port>/`
5. On exit, the temp dir is deleted (best-effort)

**Implication for nalar:** we need to add static-file serving to nalar. This is a separate change to `src/main.zig` (~100 lines, well-trodden territory). The desktop app's `build.zig` will need to depend on this nalar change being merged first.

## Per-platform implementation

| Platform | Native shim file | System libraries | Event loop |
|----------|------------------|------------------|------------|
| **Linux** | None — all in Zig via `@cImport` on `<webkit2/webkit2.h>` and `<gtk/gtk.h>` | `webkit2gtk-4.1` (or fallback to 4.0), `gtk-3-lib`, `libsoup-3.0` | `gtk_main()` / `gtk_main_quit()` |
| **macOS** | `platform/macos/nalar_webview.mm` (Objective-C++) | `Cocoa.framework`, `WebKit.framework` | `[NSApp run]` / `[NSApp terminate:]` |
| **Windows** | `platform/windows/nalar_webview.cpp` (C++) | `WebView2Loader.dll` (~120 KB, linked in), `ole32`, `user32` | `GetMessage` / `DispatchMessage` Win32 loop |

The macOS `.mm` and Windows `.cpp` are the only platform-specific native code. They implement the 3 C functions. Estimated size: ~300 LOC each, both well-trodden patterns (Tauri's wry, webview-rs all do this).

## Build system (`build.zig` additions)

```
"build:webapp"        → b.addSystemCommand(["bun", "run", "build"]) in src/apps/desktop
                         (depends on src/apps/desktop/node_modules existing — fail fast with a clear message if not)
"build:desktop-app"   → compile nalar-desktop, depends on "build:webapp"
"run:desktop-app"     → b.addRunArtifact(desktop_exe), depends on "build:desktop-app"
"test:desktop-app"    → b.addTest on port allocator, CLI parsing, subprocess healthcheck
"install"             → install nalar + nalar-desktop to zig-out/bin/
```

### Asset embedding strategy (comptime directory walk)

1. `build:webapp` runs `bun run build` → produces `src/apps/desktop/dist/` (with hashed filenames like `assets/index-abc123.js`)
2. A small comptime helper in `build.zig` walks `src/apps/desktop/dist/` using `std.fs.cwd().readDir` and writes a generated file `src/apps/desktop_app/embedded/webapp_assets.zig` containing:
   ```zig
   pub const assets: []const Asset = &.{
       .{ .path = "/", .content = "<index.html contents>", .mime = "text/html" },
       .{ .path = "/assets/index-abc123.js", .content = "<js contents>", .mime = "application/javascript" },
       // ... one entry per file
   };
   ```
3. The Zig code uses this generated array at compile time
4. At runtime, the desktop app walks `assets` and writes them to a temp dir before spawning nalar
5. nalar (with the new static-serving feature) serves them

The codegen step runs in `build.zig` itself, not as a shell command — Zig has all the file I/O primitives we need.

## Error handling

| Failure | Behavior |
|---------|----------|
| `nalar` binary not found | Log to stderr, exit 2 with message showing the search path tried |
| `nalar` fails to spawn (permission, etc.) | Log errno, exit 3 |
| `nalar` doesn't respond on health within 10s | Kill nalar, log captured stderr, exit 4 |
| `webview_create` returns null | Kill nalar, log platform error, exit 5 |
| Webview crashes mid-run (rare) | Try to kill nalar, exit 6 |
| `nalar` crashes mid-run | Webview shows connection error. We detect via a 1-Hz background health-check thread. Attempt one restart of nalar (with the same port, which may collide — accept the risk; if it does, give up). On second failure, exit 7. |
| SIGINT (Ctrl+C in terminal where nalar-desktop was launched) / window close | SIGTERM nalar, wait up to 2s, SIGKILL if still alive, exit 0 |
| Couldn't extract embedded assets to temp dir | Log, exit 8 |
| Couldn't clean up temp dir on exit | Log a warning, exit 0 (don't fail because of cleanup) |

All platform errors use `std.log.scoped(.desktop_app)` for consistent prefixing. The captured `nalar` stderr is logged only on failure to keep success-path output clean.

## Testing

This is mostly an integration surface. Strategy:

### Unit tests (in `test:desktop-app`)

- **Port allocator:** find-free-port returns a port that's actually free; EADDRINUSE retry logic
- **CLI arg parsing:** every flag is recognized; defaults match; invalid values produce clear errors
- **Subprocess healthcheck:** timeout fires after 10s when target is unreachable; succeeds on first 200; retries on connection-refused
- **Asset extraction:** correct paths in temp dir; correct mime types; cleanup deletes the temp dir
- **Asset manifest codegen:** given a fake dist/ directory, the generated Zig file has the expected entries

### Smoke test (CI, headless)

CI runs `bun install && bun run build && zig build nalar-desktop` on Linux/macOS/Windows runners, then:

- **Linux:** Xvfb provides a virtual display; `nalar-desktop --smoke-test` boots the webview, waits 2s, verifies the window is up, exits 0
- **macOS:** The CI runner has a real display; smoke-test runs natively
- **Windows:** Virtual display via the runner; smoke-test runs

`--smoke-test` is a thin mode: it skips the `gtk_main`/`NSApp.run`/`Win32` blocking and instead polls the window-state for 2s.

### Manual test plan (per platform, before release)

1. Open the app — verify window appears
2. Create a session, send a message — verify SSE streaming works
3. Resize the window — verify layout reflows
4. Close the window — verify `ps aux | grep nalar` shows no leftover nalar process
5. Kill nalar manually while the app is running — verify the app exits within a few seconds
6. Re-launch the app after a crash — verify no leftover temp dirs

## Distribution & runtime dependencies

### v1 distribution: two binaries side by side

```
/usr/local/bin/nalar            ← existing
/usr/local/bin/nalar-desktop    ← new
```

`zig build install` puts both in `zig-out/bin/`. The user copies them or uses a one-line installer script.

### Runtime system dependencies

| Platform | Runtime system deps | Bundled in nalar-desktop? |
|----------|--------------------|--------------------------|
| **Linux** | `webkit2gtk-4.1` + `gtk-3` + `libsoup-3.0` (already on most desktops; on minimal servers, `apt install libwebkit2gtk-4.1-dev` etc. is needed) | Vue dist: yes (embedded). `nalar`: no (separate binary). |
| **macOS** | None — Cocoa + WebKit are system frameworks on every macOS install | Vue dist: yes. `nalar`: no. |
| **Windows** | WebView2 Runtime (preinstalled on Win 10+ / Server 2019+, otherwise a 100 MB one-time download — Microsoft's `EvergreenBootstrapper`) | Vue dist: yes. `WebView2Loader.dll`: yes (linked in). `nalar`: no. |

### Packaging (out of scope for v1)

AppImage / `.deb` for Linux, signed `.app`/`.dmg` for macOS, MSIX/`.exe` for Windows. These are a separate packaging initiative. v1 ships as "two binaries, copy them somewhere on PATH."

## Prerequisites (blocks)

For this design to be implementable, the following change to `nalar` is required first:

**Add a static-file serving feature to `nalar`** — a `--static-dir <path>` flag that makes nalar serve the contents of the given directory at `/` (with proper mime types, range support, and the right precedence vs. `/api/*`). Without this, the desktop app has no way to serve the embedded Vue dist/.

Estimated scope: ~100 lines of new Zig code in `src/main.zig` (or a new `src/modules/static_files.zig` module). Independently useful (e.g., for serving a docs site, for serving any nalar UI variant).

This prerequisite is **not part of the desktop-app implementation plan** — it's a separate change to `nalar` that should be merged first.

## Anti-patterns avoided

- **Did not pick WebUI / Tauri / wry** — those are wrappers; user wanted pure Zig with native bindings for full control and minimal dependencies
- **Did not pick in-process nalar refactor** — would have required a multi-week refactor of nalarcore + redesign of SSE streaming; deferred as Option B for "later if we want a single-purpose desktop app"
- **Did not bundle nalar inside nalar-desktop** — keeps the two binaries cleanly separated, makes development of each in isolation easy, and lets users upgrade them independently
- **Did not implement JS↔Zig IPC in v1** — YAGNI; can be added incrementally without breaking v1
- **Did not implement dev mode in v1** — preserves the simple, single-purpose "production-only" wrapper; devs use the existing `bun dev` + `nalar` browser workflow
