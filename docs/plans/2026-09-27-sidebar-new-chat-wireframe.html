Wireframe — sidebar New Chat → default project

Task task_1790528102260_4  ·  Plan docs/plans/2026-09-27-sidebar-new-chat-default-project.md
One click in the top-left sidebar creates a chat session inside the active workspace's default project — an item_type = 'agent' workspace item whose path is the user's $HOME, created on demand and guaranteed to exist for every workspace. Colours and spacing are the real sidebar tokens; the 210 px sidebar is drawn narrow so the header/action/recents geometry is legible at this size.

The chevron is the trap. It is position:absolute; top:16 (64 px) today — pinned to the header's bottom edge. A 40 px row underneath pushes its content to 88 px, so the chevron would land on top of the New Chat row and swallow clicks. It must move to top-24 (96 px) — 8 px clear — in both expanded and collapsed states. The amber badge on the left panel marks the collision.

4 — One click, end to end

Step 1 · no-op on the happy path
Store already holds the is_default = 1 item
The workspace list is loaded with the app, so this is a local find — no network, no spinner flash.
→
Step 2 · cold path only
POST /api/workspaces/:ws/default-project
Idempotent. Returns the existing default, or creates the agent item + its agents sibling + tool seed in one transaction.
→
Step 3
createAndOpenStandardChat(ws, defaultId)
The existing helper — reused verbatim, not reimplemented. addTask(name:'New Chat') + race guard.
→
Step 4 · the URL is the state
router.replace → /app/{ws}/projects/{default}/chat/{task}
Deep-linkable, refresh-safe, Back/Forward-correct. No local ref holds "which chat is open".
→
Step 5 · server, on first message
cwd resolves to $HOME
No cwd plumbing: the existing chain falls task.cwd (empty) → item.path — which is $HOME. The header shows ~/.
A chat is a task. Migration 052 dropped workspace_item_tasks.session_id; the invariant is task.id == session.id, and the sessions row is created lazily on the first chat message. So "create a new session" needs no session endpoint at all.

5 — Decisions the wireframe depends on

Proposing
  • D1 item_type = 'agent' — the task's "agent mode"; also the only type whose + already goes straight to a Standard Chat.
  • D3 path = $HOME, resolved server-side. Empty/non-absolute home is a hard error, never a silent "" — that would fall through to a /tmp sandbox and the agent would run somewhere the user never asked for.
  • D5 One default per workspace, enforced by a partial unique index (WHERE is_default = 1), not a convention. A double-click cannot produce two.
  • D6 A brand-new chat appears under the project immediately, and in Recents after the first message — exactly like the project + does today. Making it appear in Recents sooner would diverge the two entry points.
Needs your call before code
  • Q1 Deleting the only default. A partial index prevents two, not zero. Left alone, deleting the only default means the next click silently re-creates one. I lean to refusing the delete (409) — a default that reappears is surprising. This is the one thing on this page I think is genuinely 50/50.
  • Q2 Should + Add Item offer a "Default" option? I propose no — the default is system-owned, not user-created.
  • Q3 Android parity? This page is desktop only. The Android drawer has its own create-chat flow.
How this gets verified. Not by starting a server and curling it. A functional test (tests/functional/sidebar_new_chat_default_project_test.py) boots a fresh binary through harness.py on a free port in 8080–8199 — never 8081 — with HOME pointed at an isolated tmpdir, then asserts that a new chat's resolved cwd is that tmpdir and not a /tmp sandbox. The whole feature is defined by where the home directory lands, and only a harness with a controlled HOME can assert that. Unit tests cover the rest: the migration's indexes, the ensure() idempotence, and seven vitest cases for the button's states.
