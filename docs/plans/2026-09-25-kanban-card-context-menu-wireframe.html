Kanban card → right-click context menu

Remove the four hover action buttons from the kanban card and move every action into the existing right-click menu — plus a new Move to column submenu so cards can be moved without drag-and-drop.

1 The problem

The card's top row carries four 24px hover buttons. A kanban column is width: 280px, so the strip takes ~100px and the task name — the one thing the card exists to communicate — truncates hard.

2 The context menu

Right-click any card below (or use the ContextMenu key after focusing one). Every action the buttons used to do is here, plus Move to column. Ordering is by frequency first and reversibility last — Delete is pinned to the bottom in red.

Try it: right-click a card · hover Move to column to open the submenu · pick a column and the card actually moves · Esc to close

3 Move to column new feature

A nested panel listing every column on the board with its live task count. The card's current column stays visible and is marked with a ● — the most common question when opening this menu is "where is it now?", and a greyed-out answer hides it. Picking a target appends the card to the end of that column, the exact same rule the drag-and-drop handler uses.

Hidden, not disabled, when there's nowhere to go. The Move to column row does not render at all when the board has fewer than two columns, or when the column list hasn't loaded yet. A submenu containing a single dead item is worse than no submenu.

Virtual scroller gotcha. The menu is teleported to body, but it lives in the card's subtree — so if the user opens the menu and then scrolls the card out of the viewport, the scroller unmounts the card and the menu dies with it. Fix: useContextMenu also dismisses on wheel and scroll (capture phase). One listener, whole class of bug gone.

5 Keyboard

The card is already role="button" tabindex="0" with Enter/Space activation. The menu is not mouse-only.

Key Action

Current column uses aria-disabled, not disabled. It stays focusable so screen readers can still announce "current column" instead of silently skipping it.

6 Button → menu mapping

Delete gets a confirm step. Moving it to the bottom of a menu is a real risk reduction, but on its own it isn't enough — the item is still one stray pick away from a lost task. The repo already has RenameTaskModal to model an confirm on. Open question for the reviewer — ship here or as a follow-up chunk.

7 Open decisions

Five calls the implementation shouldn't make on its own.

  1. Confirm-on-delete — in this change, or a follow-up chunk?
  2. Which buttons go? The plan removes all four. Keeping the pin button is defensible — pinning is a one-click, high-frequency action.
  3. Double-click = details? A discoverable, menu-free route to the action most affected by this change. Needs a dblclick-vs-click guard so it doesn't double-fire.
  4. One-time hint toast after shipping, so existing users learn the menu exists — otherwise the removal is a silent capability loss for everyone who never used right-click.
  5. Sidebar rows (WorkspaceItemTaskRow.vue, 3 buttons) — in this change, or a follow-up? They're the narrower surface, so the strip hurts proportionally more, but they're also the primary navigation surface and a bigger blast radius.
Scope boundaries. Not in this plan: reordering within a column from the menu (drag covers it) · moving to a different board (different endpoint, different data model) · unassign a card out of every column (the board filters unassigned tasks out entirely, so the card would just vanish).
