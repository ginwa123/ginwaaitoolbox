# Remove `skill_name` Parameter from `get_skill` Tool

> **For agentic workers:** REQUIRED: Use superpowers:subagent-driven-development (if subagents available) or superpowers:executing-plans to implement this plan. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Remove the `skill_name` input parameter from the `get_skill` agent tool, leaving `path` (and `is_global`, which is preserved for forward compatibility even though `loadSkillByName` will be removed) as the only inputs.

**Architecture:** The current tool accepts either `skill_name` (look up a skill by its registered name in local/global skills directories) or `path` (load a skill file directly from disk). The `path` argument is more general — the LLM can construct a path from the directory listings returned by `list_skills`, and the file-based loader doesn't need a separate code path that goes through `parse_skill` and the skills directory conventions. The minimal, surgical change is to drop the `skill_name` branch and its dedicated `loadSkillByName` helper, keeping the file-based `loadSkillFromPath` as the only code path.

**Tech Stack:** Zig 0.15.2, JSON-schema tool definitions (`schemas.zig`), Zig standard library `std.Io`, `std.testing`. Vue 3 + TypeScript (frontend — see "Frontend impact" section below; **no code changes required**, but verified).

## Background

### Current state of `get_skill` (`src/modules/agent/tools/get_skill.zig`)

- `GetSkillInput` struct (lines 10-17) has three fields: `skill_name`, `path`, `is_global`.
- The `get_skill_tool` JSON schema (lines 30-57) declares 3 properties; the `required` list (line 54) is already `&.{ "path", "is_global" }` — `skill_name` was never in `required`, so no caller was strictly required to send it.
- `execute_get_skill_to_string` (lines 62-75) checks `input.path` first, then `input.skill_name`. If neither is set, returns `error.InvalidInput`.
- `loadSkillByName` (lines 126-189) is the only consumer of `input.skill_name`; it calls `skills.parse_skill(...)` which scans the local/global skills directories. After the change, this function becomes dead code (no public caller), so it is removed too.
- `loadSkillFromPath` (lines 87-121) is the surviving code path. It extracts `skill_name` from the file's basename for the XML output tag — this internal `skill_name` variable is **unrelated** to the input parameter and stays.

### What stays untouched

- `GetSkillResult.skill_name` (line 21) — this is an *output* field, used in the `<skill_name>...</skill_name>` XML tag. Keep it.
- The `<skill_name>...</skill_name>` XML output tags in both loaders — they're part of the wire format, parsed by `tool_registry.zig:298-305` and `handle_tool.zig:277-287` for auto-save to `session_skills`. Do not change them.
- `parse_skill` and `list_skills_from_dir_path` in `skills.zig` — still used by other tools (`list_skills`, `view_skill` via `viewSkillFromPath`).
- `tool_registry.zig:execGetSkill` — the only thing it does with the parsed `GetSkillInput` is pass it through. The JSON-deserialization of the arguments just becomes stricter (extra fields are silently ignored by `std.json.parseFromSlice`, so old LLM responses still won't crash).
- The `path` field's behavior (absolute and relative paths resolved against cwd) — unchanged.

### Why keep `is_global` in the struct

The user request is narrowly scoped to `skill_name`. The `is_global` field is still useful in theory (e.g. if a future change adds a directory-only mode), but more importantly removing it would cascade into a second public-API change with no current consumer. YAGNI: leave it. The new tests will not exercise it (because `loadSkillByName` is gone), but the field stays for forward compatibility. (If you'd rather remove it now, the changes are mechanical: drop the field, drop the schema entry, drop the `schema declares is_global property` test, and the changes for the loaded test become even simpler — say so and I'll do it.)

```zig
/// Execute the get_skill tool
/// Returns an XML string with the skill content or error message
/// Caller owns the returned memory and must free it with allocator.free()
pub fn execute_get_skill_to_string(allocator: std.mem.Allocator, io: std.Io, input: GetSkillInput, environment: ?*const std.process.Environ.Map) ![]const u8 {
    // Check if path is provided - load from file
    if (input.path) |path| {
        return loadSkillFromPath(allocator, io, path);
    }

    // Otherwise try to parse by skill name
    if (input.skill_name) |skill_name| {
        return loadSkillByName(allocator, io, skill_name, input.is_global, environment);
    }

    // No skill_name or path provided
    return error.InvalidInput;
}
```

to:

```zig
/// Execute the get_skill tool
/// Returns an XML string with the skill content or error message
/// Caller owns the returned memory and must free it with allocator.free()
pub fn execute_get_skill_to_string(allocator: std.mem.Allocator, io: std.Io, input: GetSkillInput, environment: ?*const std.process.Environ.Map) ![]const u8 {
    _ = environment; // kept for signature compatibility; not used by the path-only code path
    const path = input.path orelse return error.InvalidInput;
    return loadSkillFromPath(allocator, io, path);
}
```

## Risks & Open Questions

- **Dead-code removal of `loadSkillByName`.** This function is a useful primitive (lookup by name, walk local+global dirs, return content) but no longer has a public caller. If you anticipate wanting to expose it again (e.g. as a private helper for a future tool), keep it. Otherwise YAGNI says delete — and the UAF regression test goes with it.
- **`is_global` is now a no-op.** It's preserved on the struct for forward compatibility but the only surviving code path (`loadSkillFromPath`) ignores it. If you'd rather remove it cleanly, do that as a follow-up — it's a strictly mechanical change (drop one struct field, drop one schema property, drop one test).
- **LLM behavior change.** Any prompts/sessions that were already sending `skill_name` will start receiving an `error.InvalidInput` from `execute_get_skill_to_string`, which surfaces in `tool_registry.zig:execGetSkill` as a generic `<error>Failed to get skill</error>` XML. The LLM's next turn should self-correct (the available `path` parameter is described in the updated tool description and prompt text), but expect a noisy first session.
- **`std.json.parseFromSlice` silently drops unknown fields.** Old `tc.function.arguments` containing `{"skill_name": "foo"}` will parse cleanly (the field is just ignored) and then `input.path == null` → `error.InvalidInput` as above. No crash.
