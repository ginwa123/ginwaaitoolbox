# `search_tool` regex query + paging — Implementation Plan

**Goal:** `search_tool`'s `query` stops being a literal substring and becomes a
regex (case-insensitive, unanchored, ASCII/byte-oriented), mirroring the `search`
agent tool's matching-mode contract: **regex by default, plus a `literal` flag**
to opt out. Results gain **`limit`/`offset` paging**, so a catalog that grows with
every connected MCP server never dumps itself into the context window. Both
`query` and `limit`/`offset` are described in terms of *why* the model needs
them, so it reaches for the right call in one try.

**Why a pattern language (the point of the task).** Substring search can only
answer "does this exact phrase appear". The agent's real question is
"which tool can do X", and X is rarely spelled one way:

| Need | Substring | Regex |
|---|---|---|
| Every MCP tool from any server that *creates* something | impossible | `^mcp_.*_create` |
| A capability whose name differs by vendor | 3 calls (`doc`, `docs`, `documentation`) | `doc\|documentation` |
| A tool that mentions two concepts in one description | impossible | `memory.*(save\|store)` |
| A word, not a fragment of a longer word | matches `searcher` too | `\bsearch\b` |
| A name that is genuinely code-shaped (`*`, `(`, `[`) | works | `literal: true` |

**Why paging.** Built-ins + every MCP server's tools can run to hundreds of
entries, and every row costs context. `limit` (default 40 = the old cap, max
200) bounds one response, `total` reports the real match count, and `<hint>`
names the `offset` that continues the listing. Out-of-range values are
**rejected with the accepted range, never clamped** — a silent clamp would
desync the model's offset arithmetic against the `total` it was shown.

**Architecture:** four edits + one new leaf module.

1. **`src/agentic_loop/progressive_regex.zig` (NEW)** — a self-contained,
   pure-Zig regex engine (Pike VM / Thompson NFA). No libc, no `rg` subprocess,
   no `regex.h`: the catalog lives in memory and must match on every platform
   (Linux/macOS/Windows) with no external binary.
2. `progressive_catalog.matchQuery` compiles the query once and matches it
   against name + description; on a pattern the engine rejects it **falls back
   to the old case-insensitive substring** and says so. `pageSlice` applies the
   `offset`/`limit` window (paging lives here, not in `matchQuery`, so the
   pre-page `total` survives).
3. `progressive_catalog.renderSearchResult` carries `<pattern_mode>`,
   `<pattern_warning>`, `<offset>`, `<limit>` and a next-offset `<hint>` — so
   neither the fallback nor the page window is ever silent.
4. `src/modules/agent/tools/progressive_tools.zig` — `literal` + `limit` +
   `offset` params, the rewritten `query` description, and the matching
   system-prompt paragraphs.
5. `tools_exec_progressive_tools.zig` threads them through and owns the
   range validation.

**Supported syntax** (documented in the tool description): literals, `.`,
`[...]` incl. ranges + `[^...]`, `\d \D \w \W \s \S`, `\b \B`, escaped
metacharacters, `* + ? {m} {m,} {m,n}` (lazy `?` accepted, meaningless for
match-existence), `( )` / `(?: )`, `|`, `^`, `$`. `$` is strict end-of-text (no
trailing-newline allowance, i.e. Python's `\Z`). Matching is byte-oriented
(ASCII case folding), so a multibyte character is matched per byte.

**Deliberately not supported:** lookarounds, backreferences, `\A \z \G`, and
unknown alphabetic escapes — all return `error.InvalidPattern` rather than
silently meaning something else. `matchQuery` then falls back to substring
matching and reports it.

**Safety:** the program is capped (`MAX_INSTRS`), so quantifier expansion cannot
blow up, and the NFA simulation (O(text × program), no backtracking) carries a
per-call step budget so a hostile pattern cannot stall the agent worker. The
catastrophic-backtracking shape `(a+)+b` is a test.
