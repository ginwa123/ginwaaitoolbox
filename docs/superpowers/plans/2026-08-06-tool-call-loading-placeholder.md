# Plan: Tool-call loading placeholder (kill "Invalid function ID" on crash)

**Task ID:** `task_1785784899843`
**Date:** 2026-08-06
**Worktree:** `worktree/tool-call-loading-placeholder` (to be created)
**Branch:** `worktree/tool-call-loading-placeholder`

---

## Symptom (user report)

After a long-running tool execution crashes the agent (or the `nalar`
process itself crashes during `bash` / `spawn_sub_agent` /
`read_file` over a flaky network, etc.), the next request to the LLM
is rejected with:

```
Invalid function ID tool call error
```

The error text is verbatim from the OpenAI API docs:

> An invalid function ID tool call error occurs when the OpenAI API
> cannot match a tool response to the original request generated by
> the model. Match IDs exactly: Ensure the `tool_call_id` in your
> tool response message matches the `id` from the assistant's
> message character-for-character. Keep the Assistant's message: You
> must include the assistant's message containing the `tool_calls`
> array in the conversation history before sending the tool results.
> Submit all tool calls: If the model requested 3 function calls in
> parallel, you must submit responses for all 3 IDs in the next request.

Quick checklist: **all tool_call_ids in the assistant message must
have matching `role=tool` rows with `tool_call_id` set, in the next
conversation payload.** If even one is missing, the API rejects.

## Root cause (traced in `handle_tool.zig`)

Today, `handle_tool` runs in **two phases**:

```zig
// Phase 1 — single INSERT (synchronous, fast):
_ = try llm_history.saveMessage(allocator, io, db, .{
    .role = agent.Role.assistant.to_str(),
    .tool_calls = tc,                        // [id_A, id_B, id_C]
    .tool_call_id = null,
    .content = res_dynamic_agent.content,
    // ... all 3 tool_call_ids persisted in ONE row
});

// Phase 2 — for-loop (each iteration may take minutes):
for (tc) |tool_call| {
    // dispatchTool can run `bash` or `spawn_sub_agent` — LONG-RUNNING
    const exec_result = try dispatchTool(ctx, tool_call);
    // saveAndSendToolResult persists ONE row per iteration:
    try saveAndSendToolResult(... tool_call.id ...);   // role=tool, tool_call_id=tool_call.id
}
```

If `dispatchTool` (or `child.kill(io)` reaping, or a worker-level
process crash, or a network hang during `read_file`) throws or
crashes between Phase 1 and the end of Phase 2, the database is
left in an inconsistent state:

- ✅ `llm_history` row exists with `role=assistant`,
  `tool_calls_json=[id_A, id_B, id_C]`, `is_feed_to_llm=1`
- ✅ `tool_call_id=A` row may exist (if tool A finished before crash)
- ❌ `tool_call_id=B` row MISSING (tool B was running when it crashed)
- ❌ `tool_call_id=C` row MISSING (tool C never started)

The next request to the LLM sends all `is_feed_to_llm=1` rows. The
OpenAI API rejects with **"Invalid function ID"** because the
assistant's `tool_calls=[A,B,C]` declares 3 IDs but only the A row
is provided. The agent is now stuck — every subsequent call fails.

The user proposed the fix:

> create all toolcalls → with xml data is_loading maybe, after
> created all, now we run the command tool like bash, spawnsubag
> agent, that can be long. If this app crash, llm calling will be
> not error function invalid id.

This is exactly the right architecture — Phase 1 must create
**all** the tool-result placeholder rows synchronously, then Phase 2
runs the long-running tools and `UPDATE`s each row in place. A crash
between Phase 1 and Phase 2 leaves the placeholders behind, which
satisfy the API contract by ID.

## Goal

The conversation payload sent to the LLM ALWAYS contains a
`role=tool` row with matching `tool_call_id` for every ID in the
preceding assistant message's `tool_calls` array — even if the
agent crashed mid-execution. Crash recovery is automatic on next
startup (replaces pending placeholders with a synthetic "tool
execution interrupted" message so the LLM can decide what to do).

## Architecture

Three changes, all in `src/ai_workflow/tui/`:

1. **Migration 068** — add `is_loading INTEGER NOT NULL DEFAULT 0`
   column to `llm_history` so we can query for stranded placeholder
   rows on startup.

2. **`llm_history.zig`** — two new helpers:
   - `saveToolResultPlaceholder(allocator, db, io, opts)` — INSERT
     a `role=tool` row with `tool_call_id=<id>`, `content=""`,
     `is_loading=1`, `is_feed_to_llm=1`. The empty content (not
     `<loading>`) satisfies the API contract because the assistant
     message declares the ID exists; the LLM just sees an empty
     tool result if it looks — which is acceptable as a "still
     running" sentinel.
   - `updateToolResult(allocator, db, tool_call_id, content,
     diffview_before, diffview_after, is_loading=0)` — UPDATE the
     row by `tool_call_id` with the real content.

3. **`handle_tool.zig`** — restructure `handle_tool()` to do
   **three phases** instead of two:

   ```
   Phase 1 (sync)  ── INSERT placeholder rows for ALL tool_calls
   Phase 2 (sync)  ── INSERT the assistant message with tool_calls
   Phase 3 (loop)  ── for each tool_call:
                       run dispatchTool
                       UPDATE the placeholder row with the result
   ```

4. **`session_init` / `worker_resume` hook** — on agent start (any
   code path that may resume a session: `delete_worker`, the SSE
   `worker created` handler, the auto-retry path, manual restart),
   call `resolveStaleLoadingToolResults(allocator, db, session_id)`
   which:
   - SELECTs `tool_call_id` rows WHERE `is_loading=1` AND
     `session_id=?`
   - For each, UPDATE content to
     `"<tool_status>interrupted</tool_status>\nTool execution
     interrupted by server restart. Please retry this action."`
     AND set `is_loading=0`. Also delete any
     `tool_calls_json`-bearing assistant row that has un-matched
     pending rows AND is the most recent assistant message (so the
     LLM only sees a clean conversation).
   - Logs a WARN with the count of recovered rows per session.

   The startup hook lives at the top of `handle_tool` (the safest
   place — runs before any new tool execution can clobber the DB).

The assistant message INSERT moves AFTER all placeholders so a
crash during Phase 1 leaves NO assistant message behind. This is
intentional — if the placeholder insert succeeds but the assistant
insert crashes, we can just rerun the assistant INSERT on retry
(idempotent: `llm_history.id` is `nanoseconds` so re-runs get new
ids, but the conversation semantics are correct because the LLM
will see the assistant+tool messages in order).

### Inline tests in `llm_history.zig` (next to each helper)

For `saveToolResultPlaceholder`:
1. INSERT placeholder with `tool_call_id="tA"` + `is_loading=1`;
   SELECT confirms the row exists with the right values.
2. INSERT a SECOND placeholder with the same `tool_call_id` —
   DB error (tool_call_id is the natural key, but we need a UNIQUE
   constraint). **Action**: add `CREATE UNIQUE INDEX IF NOT EXISTS
   idx_llm_history_tool_call_id ON llm_history(tool_call_id)
   WHERE tool_call_id IS NOT NULL AND tool_call_id != ''` in the
   migration to enforce.
3. INSERT placeholder with `tool_call_id=""` → succeeds, treated
   as the assistant's own row (no constraint violation because the
   partial index excludes empty strings).

For `updateToolResultById`:
1. UPDATE an existing placeholder with the actual content +
   `is_loading=0`; SELECT confirms the row's `response_content`,
   `diffview_*`, `is_loading` are updated in place.
2. UPDATE a non-existent `tool_call_id` is a no-op (0 rows
   affected, no error).
3. UPDATE leaves `created_at` and `created_iso` untouched (we
   do NOT want the timestamp to drift from the placeholder's
   "started at" time).

For `resolveStaleLoadingToolResults`:
1. Session with 3 stranded placeholders → all 3 are updated to
   "interrupted" content + `is_loading=0`; SELECT confirms.
2. Session with 0 stranded placeholders → no-op (0 rows affected).
3. Session with mix of stranded + already-resolved placeholders →
   only stranded ones updated; resolved ones untouched.
4. Multiple sessions → only the target session is touched
   (`WHERE session_id = ?` filter works).

### `handle_tool_loading_placeholder_test.zig` (new)

Behavioural test that exercises the full 3-phase pattern:

1. Call `handle_tool` with 3 mock tool_calls; mock `dispatchTool`
   for each to return a synthetic result. Assert:
   - 1 assistant row + 3 tool rows in DB
   - Each tool row's `tool_call_id` matches one of the 3 IDs
   - Each tool row's `response_content` matches the mock result
   - All rows have `is_loading=0`
   - All rows have `is_feed_to_llm=1`

2. Call `handle_tool` with 3 tool_calls where the FIRST
   `dispatchTool` throws `error.SimulatedCrash`. Assert:
   - 1 assistant row + 3 placeholder tool rows in DB
   - 2 placeholders have `is_loading=1` (the crashed + never-
     started ones)
   - The 3rd placeholder (which the crashed tool ran before the
     crash) — actually we need to simulate this more carefully;
     we throw BEFORE the UPDATE, so it stays at `is_loading=1`
   - The session can be "recovered" by calling
     `resolveStaleLoadingToolResults` directly; all 3 are now
     `is_loading=0` with "interrupted" content.

3. Idempotency: call `handle_tool` twice with the same
   `tool_call_id`s — second call is rejected with the UNIQUE INDEX
   error (test asserts the error is surfaced cleanly).

4. The `getMessages` query (which filters by
   `is_feed_to_llm=1 OR IS NULL`) still returns all rows including
   placeholders, satisfying the LLM API contract. We confirm by
   reading back the conversation and asserting every
   `tool_call_id` from the assistant's `tool_calls_json` has a
   matching tool row in the result list.

## Out of scope (deferred to follow-ups)

- **Per-tool recovery strategy**: for v1, all stranded tool results
  are replaced with a generic "interrupted" message. A future
  improvement could attempt to re-run the tool if its
  `tool_calls[i]` arguments are recoverable (most long-running
  bash / spawn_sub_agent commands are NOT idempotent, so blind
  re-run is risky — defer until the user asks).
- **Migration backfill for existing stranded rows**: the
  `resolveStaleLoadingToolResults` helper handles any existing
  stranded rows on next startup, but we don't pre-populate any
  rows. If a user upgrades mid-crash (already-broken state), the
  helper runs and fixes them — no separate backfill migration
  needed.
- **LLM-side retry on interrupted**: we just give the LLM the
  "interrupted" text and let it decide. We don't retry the tool
  on the LLM's behalf (OpenAI doesn't support that, and the LLM
  may want to ask the user first).
- **Streaming the placeholder content**: the placeholder is
  committed with empty content. We could stream a live
  `<pending>...</pending>` update via SSE so the UI shows
  "running…" in real time. Defer until the user asks — the
  current behaviour (empty content + SSE `worker created` event)
  is good enough.
- **Frontend "tool running" indicator**: the chat view already
  shows a "Queue" / "Stop" button while the agent runs, which
  doubles as the "tool running" indicator. No new UI needed.

## Why NOT this design (alternatives considered)

1. **Wrap each tool dispatch in its own try-catch + saveMessage
   AFTER dispatch** — that's the current behaviour. Fails on crash.
2. **Write a marker row to a separate `tool_call_pending` table,
   not `llm_history`** — adds a JOIN to every `getMessages` call,
   duplicates the FK relationships, and complicates the wire
   shape. The flag column is cleaner.
3. **Wrap `dispatchTool` in a child process so the parent can
   reap + recover the output even on parent crash** — does NOT
   fix the problem (parent crash still loses the tool result).
   Useful for sandboxing, but orthogonal to this bug.
4. **Add a startup-time catch-up: if the previous run's assistant
   message has unmatched tool_call_ids, synthesize "interrupted"
   results before the next LLM call** — this is exactly what
   `resolveStaleLoadingToolResults` does. The 3-phase rewrite
   PLUS this catch-up is the belt-and-suspenders approach we want.
