Sub-Agent Peek Progress — Wireframe

Frontend-only feature for the nalar desktop app. Clicking 👁 on a row in the spawn_sub_agent tool card opens a right-side slide-over panel showing the sub-agent's live progress without leaving the parent chat. Paired with plan 2026-06-29-sub-agent-peek-progress.md.

After the parent chat's LLM calls spawn_sub_agent, the existing tool card renders. Each agent row gets a new 👁 peek button between the inherited-context badge and the success/failed label.

What the user sees while the sub-agent works
  • Header: "Sub-agent" label + agent name + violet pulsing dot + "Streaming…". Instruction is truncated to its first ~100 chars with a title tooltip for the full text.
  • Open full button: closes the panel and navigates to /app?view=chat&session=subagent_… (the sub-agent's chat view loads in the main area).
  • ✕ close button + ESC keybind: tears down the SSE connection. (Verified by the onUnmounted test in the composable.)
  • Messages auto-scroll to the bottom as new chunks arrive. Each message bubble is rendered with the same color semantics as the parent chat (user / assistant / tool) for visual continuity.
  • Streaming indicator: assistant messages that haven't finished have a blinking ▍ cursor at the end. Tool calls get a small violet chip with the tool name.
  • Footer: session_id (full, monospace) + token count. Updates live as chunks arrive (when the backend includes total_tokens in the SSE payload).
  • The parent chat (behind the overlay, dimmed to ~40% opacity) is intact — closing the panel returns to it with no scroll/render state lost.

Scene 4 · Peek panel — initial fetch failed

If the backend can't return the sub-agent's history (network drop, session deleted mid-load, auth miss), the panel shows an error banner with a Retry button. The composable's reload() action is wired to it.

What you see on error
  • Red banner pinned just below the header, above the messages area. Background: rgba(239, 68, 68, 0.1), border: rgba(239, 68, 68, 0.3).
  • The banner shows the raw error message from apiFetch + a "Retry" button. Clicking Retry calls the composable's reload() action which re-runs the initial history fetch.
  • The header status badge stays red ("Error") until Retry succeeds.
  • The message area shows an italic muted "Couldn't load…" placeholder instead of being empty (so the layout doesn't collapse).
  • If the SSE connection is already open when the initial fetch fails, it stays open (best-effort) — Retry re-runs the fetch but doesn't tear down the SSE. This is the composable's reload() implementation.

Why this is frontend-only

The backend already exposes everything we need:

  • GET /llm/session/{sid}/messages (existed since v0; reuses session_messages_get.zig).
  • GET /api/events?channels=llm:{sid} (existed since the SSE unification; routes per-session chunks via unified_events_sse.zig).
  • The parent_session_id column on llm_history already records the parent↔sub-agent link (migration 044-family).
  • The worker table already keys each sub-agent by its session_id.

The peek panel is a consumer of that existing infrastructure — it doesn't add backend surface area, doesn't change any DB schema, and doesn't require a new endpoint.

Out of scope (per the plan's "Locked decisions")

  • Multi-agent tabs in one panel — v2.
  • Notifications when a peeked sub-agent completes while the panel is closed — v2.
  • Stop / cancel from the peek panel — v3.
  • Showing the full system prompt — security review pending.
  • A persistent "active sub-agents" sidebar widget — separate feature.
