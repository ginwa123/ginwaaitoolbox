# nalar desktop — `bun run build` is the TypeScript Type-Check, Not `vitest run`\n\n`bunx vitest run` runs the test suite but does **not** run `vue-tsc` for strict\nTypeScript type checking. The test files pass type-erasure at runtime, so\nTS errors like `Object is possibly 'undefined'` (TS2532) only surface during\na full `vue-tsc` pass — which happens during `bun run build`, not during\n`bunx vitest run`.\n\n## Symptom\n\nA code reviewer approves a TS change because `vitest run` passes (all tests\ngreen), but the next `bun run build` fails with multiple `TS2532: Object is\npossibly 'undefined'` errors in the new test file. The bug was always there\nfrom the moment the code was written; `vitest run` just doesn't see it.\n\n## Why\n\nVitest is a test runner. It compiles each test file to JS at runtime, with\nTypeScript's type checking effectively elided (Vitest uses `esbuild` for\ntransform, which strips types without checking them). The `vue-tsc` step that\nDOES check types only runs in `bun run build`.\n\n## Fix\n\n**Always run `bun run build` (NOT just `bunx vitest run`) when reviewing or\nverifying TypeScript code changes in this project.** The project's NALAR.md\nhas a memory rule about `bun run build` vs `bun run build-only`; this memory\nextends it: even the test-pass criterion must include a successful build, not\njust test runs.\n\n## Concrete test command sequence\n\n```\ncd src/apps/desktop\ntimeout 120 bun run build 2>&1 | tail -n 20      # type-check + bundle\ntimeout 120 bunx vitest run 2>&1 | tail -n 20    # unit tests\n```\n\nIf both are clean, the change is good. If `bun run build` fails with TS\nerrors, the change is broken regardless of what `vitest run` says.\n\n## When This Bites\n\n- Reviewing a TypeScript change where the implementer only ran tests\n- Writing spec files with optional-chaining shortcuts that don't propagate\n  to property access (e.g. `result?.[0].name` is `T | undefined` — needs\n  `result?.[0]?.name`)\n- The `??` operator on nullish-coalesced values (`a ?? b` where both can\n  be undefined) — `vue-tsc` flags this in strict mode\n- Any test that mocks types with `as` casts that the runtime never\n  actually exercises\n\n## How to verify\n\nIf you only ran `bunx vitest run` and the tests pass, **before approving the\nchange**, run `bun run build` and check the output for TS errors. This is\nthe project's authoritative type-check.\n
